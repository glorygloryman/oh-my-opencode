# 宣言

Oh My OpenCode 背后的原则与理念。

---

## 人工干预是失败信号

**人在循环中 = 瓶颈**
**人在循环中 = 瓶颈**
**人在循环中 = 瓶颈**

想想自动驾驶。当人类必须接管方向盘时，那不是一项功能——而是系统的失败。车辆无法独自应对这种情况。

**为什么编程会有所不同？**

当你发现自己：
- 修复 AI 半途而废的代码
- 手动纠正明显的错误
- 一步步指导代理完成任务
- 反复澄清相同的需求

……那不是"人机协作"。那是 AI 未能完成它的工作。

**Oh My OpenCode 建立在这个前提之上**：在代理工作期间，人工干预本质上是一个错误信号。如果系统设计正确，代理应该能够完成工作，而不需要你盯着它。

---

## 无法区分的代码

**目标：代理编写的代码应该与高级工程师编写的代码无法区分。**

不是"需要清理的 AI 生成代码"。不是"一个好的起点"。而是真正的、最终的、可直接用于生产的代码。

这意味着：
- 严格遵循现有代码库的模式
- 无需提示就能正确处理错误
- 测试真正测试正确的内容
- 没有 AI 烂摊子（过度工程、不必要的抽象、范围蔓延）
- 只在有价值时添加注释

如果你能分辨出一个提交是由人还是代理完成的，那么代理就失败了。

---

## Token 成本 vs 生产力

**如果显著提高生产力，更高的 token 使用量是可以接受的。**

使用更多 token 来：
- 让多个专业代理并行研究
- 无需人工干预即可完全完成工作
- 在完成前彻底验证工作
- 跨任务积累知识

……当这意味着 10 倍、20 倍或 100 倍的生产力提升时，是值得的投资。

**然而：**

不追求不必要的 token 浪费。系统优化于：
- 对简单任务使用更便宜的模型（Haiku、Flash）
- 避免冗余探索
- 跨会话缓存学习内容
- 在收集到足够上下文时停止研究

Token 效率很重要。但不能以牺牲工作质量或人类认知负荷为代价。

---

## 最小化人类认知负荷

**人类只需要说出他们想要什么。其他一切都是代理的工作。**

两种实现方法：

### 方法一：Prometheus（访谈模式）

你说："我想添加认证功能。"

Prometheus：
- 研究你的代码库以了解现有模式
- 基于实际发现提出澄清性问题
- 揭示你没有考虑到的边缘情况
- 在你做出决策时记录下来
- 生成完整的工作计划

**你提供意图。代理提供结构。**

### 方法二：Ultrawork（直接做模式）

你说："ulw 添加认证功能"

代理：
- 找出正确的方法
- 研究最佳实践
- 按照约定实现
- 验证一切正常
- 持续工作直到完成

**你提供意图。代理处理一切。**

在这两种情况下，人类的工作是**表达想要什么**，而不是管理如何完成。

## 可预测、可持续、可委派

**理想的代理应该像编译器一样工作**：markdown 文档输入，可运行的代码输出。

### 可预测

给定相同的输入：
- 相同的代码库模式
- 相同的需求
- 相同的约束

……输出应该是一致的。不是随机的，不是令人惊讶的，不是你未要求的"创造性"。

### 可持续

工作应该能在中断后继续：
- 会话崩溃？用 `/start-work` 恢复
- 需要离开？进度被跟踪
- 跨天项目？上下文被保留

代理维护状态。你不必这样做。

### 可委派

就像你可以把任务分配给一个有能力的团队成员并相信他们会处理好一样，你应该能够委派给代理。

这意味着：
- 明确的验收标准，独立验证
- 出现问题时自我纠正的行为
- 仅在真正需要时升级（向 Oracle、向用户）
- 完整的工作，不是"基本完成"

---

## 核心循环

```
人类意图 → 代理执行 → 验证结果
      ↑                              ↓
      └──────── 最小化 ─────────────┘
         (仅在真正失败时干预)
```

Oh My OpenCode 的一切都是为了让这个循环工作：

| 功能 | 目的 |
|------|------|
| Prometheus | 通过智能访谈提取意图 |
| Metis | 在歧义变成 bug 之前捕获它们 |
| Momus | 在执行前验证计划的完整性 |
| Orchestrator | 无需人工微观管理协调工作 |
| Todo Continuation | 强制完成，防止"我完成了"的谎言 |
| Category System | 无需人工决策即可路由到最优模型 |
| Background Agents | 并行研究而不阻塞用户 |
| Wisdom Accumulation | 从工作中学习，不重复错误 |

---

## 实践中的意义

**你应该能够：**

1. 描述你想要什么（高层次或详细，由你选择）
2. 如需要，让代理访谈你
3. 确认计划（或让 ultrawork 处理）
4. 离开
5. 回来看到完成的、验证过的、可直接用于生产的工作

**如果你做不到这些，系统中有些东西需要改进。**

---

## 我们正在构建的未来

一个这样的世界：
- 人类开发者专注于构建**什么**，而不是**如何**让 AI 构建它
- 代码质量独立于谁（或什么）编写它
- 复杂项目与简单项目一样容易（只是需要更长时间）
- "提示工程"变得像"编译器调试"一样过时

**代理应该是不可见的。** 不是隐藏意义上的不可见，而是它就是能工作的意义上的不可见——像电力、像自来水、像互联网。

你打开开关。灯亮了。你不会去想电网。

这就是目标。
