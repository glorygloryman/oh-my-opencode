# start-work-hook.ts 机制解析

> 生成时间：2026-02-24 14:06:00
> 来源：OpenCode 会话总结

## 背景与问题

用户希望深入理解 `oh-my-opencode` 插件中 `start-work-hook.ts` 的实现逻辑，关注两个核心问题：
1. 该 Hook 如何与 OpenCode 交互，利用了哪些机制
2. start-work 功能的内部逻辑及依赖的上下文信息

## 讨论要点

### 1. 与 OpenCode 的交互机制

**Hook 注册与调用链路**：
```
用户输入 /start-work "plan-name"
    ↓
OpenCode chat.message 事件触发
    ↓
plugin/chat-message.ts (handler)
    ↓
调用 hooks.startWork["chat.message"]
    ↓
start-work-hook.ts 中的 hook 函数执行
```

**利用的 OpenCode 机制**：

| 机制 | 说明 |
|------|------|
| `chat.message` 事件 | OpenCode 标准 hook 事件，每次用户消息时触发 |
| `output.parts` 操作 | 通过修改 `output.parts` 向 AI 注入系统上下文 |
| `ctx.directory` | 插件上下文中的工作目录，用于读写状态文件 |
| `input.sessionID` | 当前会话唯一标识，用于追踪多会话工作 |

**触发条件**：通过检测 `<session-context>` 标签区分命令执行与普通消息（第 64-68 行）

### 2. start-work 核心逻辑流程

**整体流程**：
```
开始
  │
  ▼
提取 <user-request> 中的计划名称
  │
  ├─► 有明确计划名？ ──► 按名称查找计划 ──► 匹配到？ ──► 创建/恢复 boulder 状态
  │                         │                    │
  │                         ▼                    ▼
  │                      未匹配              已完成的计划？
  │                         │                    │
  │                         ▼                    ▼
  │                      显示可用计划           提示已完成
  │                      列表供选择
  │
  └─► 无计划名 ──► 检查现有 boulder 状态
                    │
                    ├─► 有未完成计划 ──► 恢复工作
                    │
                    └─► 无/已完成 ──► 查找所有计划
                                          │
                                          ├─► 0 个 ──► 提示创建
                                          ├─► 1 个未完成 ──► 自动选择
                                          └─► 多个未完成 ──► 列出供选择
```

**关键步骤**：

1. **提取用户请求的计划名**：从 `<user-request>` 标签中提取，并移除 `ultrawork`/`ulw` 关键词
2. **Agent 切换**：自动将当前会话 agent 标记为 `"atlas"`（第 74 行）
3. **计划查找**：支持精确匹配和部分匹配（不区分大小写）
4. **状态管理**：通过 `boulder.json` 文件持久化工作状态
5. **上下文注入**：通过修改 `output.parts` 向 AI 注入工作上下文信息

### 3. 依赖的上下文信息

**文件系统状态**：
| 路径 | 用途 |
|------|------|
| `{project}/.sisyphus/plans/*.md` | Prometheus 生成的计划文件 |
| `{project}/.sisyphus/boulder.json` | 当前活跃计划的状态持久化 |

**核心依赖模块**：

| 模块 | 路径 | 用途 |
|------|------|------|
| `boulder-state` | `src/features/boulder-state/` | 状态读写、计划查找、进度计算 |
| `claude-code-session-state` | `src/features/claude-code-session-state/` | 会话 agent 标记 |
| `logger` | `src/shared/logger` | 调试日志 |

**BoulderState 数据结构**：
```typescript
interface BoulderState {
  active_plan: string    // 计划文件绝对路径
  started_at: string     // ISO 时间戳
  session_ids: string[]  // 所有参与该计划的会话 ID
  plan_name: string      // 计划名（从文件名提取）
  agent?: string         // 使用的 agent 类型
}
```

**进度计算方法**：通过解析 markdown 文件中的 checkbox（`- [ ]` 和 `- [x]`）统计完成度

### 4. 四种典型场景处理

| 场景 | 输入示例 | 处理结果 |
|------|----------|----------|
| 明确指定计划名且匹配 | `/start-work "fix-bug-123"` | 创建新的 boulder.json，切换到该计划 |
| 明确指定计划名但未匹配 | `/start-work "non-existent"` | 显示所有未完成计划列表供选择 |
| 无计划名但有活跃状态 | `/start-work` | 恢复之前的计划，追加当前 session ID |
| 无计划名且无活跃状态 | `/start-work` | 自动选择（唯一未完成）或列出供选择 |

## 结论与决策

`start-work-hook.ts` 是 **Sisyphus 工作流系统的入口点**，承担以下职责：

1. **命令拦截**：利用 OpenCode 的 `chat.message` hook 拦截 `/start-work` 命令
2. **上下文注入**：通过操作 `output.parts` 向 AI 注入工作上下文
3. **状态管理**：通过 `boulder.json` 实现跨会话的计划追踪
4. **Agent 切换**：自动将会话标记为 `"atlas"` 进入执行模式
5. **计划匹配**：支持精确/模糊匹配用户指定的计划名

该 Hook 是连接用户命令、计划管理（Prometheus）和执行编排（Atlas）的关键枢纽。
