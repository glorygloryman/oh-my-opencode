# oh-my-opencode 插件魔改与部署共享指南

本文档介绍了对 `oh-my-opencode` 插件进行二次开发（魔改）后，如何在本地生效运行，以及如何与团队或其他开发者共享你的成果。共包含三种常见的部署与操作方案。

## 方案一：本机开发与部署最快路径（推荐用于本地开发自测）

在进行插件的本地定制化开发时，最有效的方法是直接让 OpenCode 读取你开发目录下的实时编译产物。这跳过了打包、上传和重新安装的步骤，且彻底解决了安装位置和缓存不同步的问题。

### 适用场景

仅在你自己的电脑上生效测试，暂时不需要分享给其他人。希望能实现代码修改后的快速闭环验证。

### 操作步骤

1. **编译本地代码**
   每次修改源代码后，你在你的源码目录下（如 `~/workspace/oh-my-opencode`）执行即可：

   ```bash
   bun install
   bun run build
   ```

2. **修改 OpenCode 全局配置**
   打开 OpenCode 的配置文件 `~/.config/opencode/opencode.json`。
3. **指向本地绝对路径**
   将 `plugin` 数组中的源插件名称（通常是 `"oh-my-opencode@latest"`），替换为你**本地源码目录的绝对路径**：

   ```json
   {
     "$schema": "https://opencode.ai/config.json",
     "permission": {
       "*": "allow",
       "external_directory": "ask"
     },
     "plugin": [
       "/Users/你的用户名/你的工作目录/oh-my-opencode"
     ]
   }
   ```

4. **验证生效**
   将 OpenCode 客户端完全退出并重新打开。之后只要你每次在本地目录执行 `bun run build` 生成最新构建后重启 OpenCode，即可直接加载你的魔改成果。

## 方案二：基于源码仓库 Fork 共享（适合特定圈子/开发者的全平台方案）

由于 `oh-my-opencode` 依赖了使用 C++ 编写的底层 Native 包（譬如 `@ast-grep/napi`），这意味着简单地直接发送一个基于你 Mac 环境打包的 `.tgz` 离线文件会导致 Windows 等其他系统的使用者运行时崩溃报错。
对于大家都是具备开发环境的协作者来说，克隆源码是规避跨平台依赖问题的最安全选择。

### 适用场景

协作者是具备 Node.js/Bun 环境的开发工程师，且使用者跨越多种不同的操作系统和芯片架构环境（M芯片、Intel等），无需构建繁杂的多平台持续发布流水线。

### 操作步骤

1. **提交代码到代码托管平台**
   将你本地修改好的代码 `commit` 并 `push` 到你自己的远程仓库分支中（如自己的 GitHub/GitLab Fork 仓库）。
2. **协作者获取源码库**
   使用者将你的远程关联仓库 `git clone` 到他们自己的本地固定目录。
3. **协作者在本地初始化构建**
   让使用者在他们的仓库目录中手动执行安装构建：

   ```bash
   bun install
   bun run build
   ```

   *(通过这一步，安装程序会通过底层针对使用者的系统环境自动拉取最合适的 Native 架构底层包)*
4. **修改 OpenCode 路径指向**
   参考「方案一」，协作者需要修改其电脑上的 `~/.config/opencode/opencode.json` 文件，将 `plugin` 值更改为其克隆到本地的那份源码库的**绝对路径**。

## 方案三：更名构建，发布至 NPM 镜像源（最地道优雅的最佳实践）

如果你想基于此建立公司内部长期维护的一套专属业务分支版本，或者是让普通业务同学使用你的成果，重新打包发布至内部或公共包管理平台是最高效的方式。最终用户修改一行配置即可开箱即用。

### 适用场景

致力于产出产品级长期维护插件。使用者只需修改配置文件里的字符串，不涉及任何 clone 源码及构建细节的操作（甚至可以在不需要手动处理环境包的情形下静默更新拉取）。

### 操作步骤

原名称 `oh-my-opencode` 已经被中心源占用注册，需建立自己的"马甲"包：

1. **为插件更换"马甲" (`package.json`)**
   - 更改 `name` 字段设定专属包名（如 `@yourcompany/oh-my-opencode` 或是 `cy-oh-my-opencode`）。
   - *（高级跨平台配置要求）* 如果你要完全保持跨平台，需要将 `package.json` 的 `optionalDependencies` 里的各平台包名也都对应挂上前缀，并同步修改根目录涉及二进制发布的相关构建脚本及 CI yml 声明文件，以确保打包出属于你前缀的 native 相关分发。
2. **发布至包管理平台**
   - **企业内部私有仓库**：如果你处在公司内网，可以直接使用 `npm publish --registry=http://你们私有的Nexus或Verdaccio地址` 进行推包及更新。
   - **公共 NPM (利用自动化 CI 流水线)**：此项目源码在 `.github/workflows/publish.yml` 里本身就预设了非常健壮的多平台并行发布系统。只要在你的个人 GitHub Fork 设置中增加 `NPM_TOKEN` Secret 配置，配合打 Git Tag 或手工触发 Workflow 就能自动完成各平台 Native 包交叉编译并上传全自动发版。
3. **他端开箱极简配置**
   无论是同事还是互联网用户，现在都不再需要下载源码。只需要去修正本地 `opencode.json`：

   ```json
   {
     "plugin": [
       "@yourcompany/oh-my-opencode@latest" 
     ]
   }
   ```

   当 OpenCode 下次启动时，将会无感知地从所指 NPM 仓库拉取你的专属包，自动解压执行。
