# Sisyphus 计划文档同步机制优化设计方案

## 1. 背景与现状

当前为了让工作进度的可见性更高，设计了一个在 `/start-work` 时自动将 `.sisyphus/plans/` 下的计划文档同步到 `project-docs/plans/` 的功能。

目前已在 `src/hooks/start-work/start-work-hook.ts` 中实现了初步的同步逻辑：通过 `readFileSync/writeFileSync` 复制文件内容，并按 `YYYY-MM-DD-{plan-name}.md` 的格式重命名，日期取自原计划文件的 `mtime`。

## 2. 现有方案深度审查与漏洞分析

经过深度审查（Code Review），发现当前粗暴的物理复制复制（Copy）方案虽然可行性得到了初步验证，但从架构演进和生命周期看，存在几个致命问题需要优化。

### 2.1 漏洞 A：状态快照不同步（致命缺陷）

* **问题所在**：当前实现在 `/start-work` 钩子触发时，仅执行一次单向的文件物理复制。在这个生命周期节点，计划的进度处于刚启动阶段。
* **最终后果**：在后续开发中，开发人员或智能体会在源文件（`.sisyphus/plans/`）中勾选已完成任务（将 `[ ]` 改为 `[x]`）。这些进度更新**完全不会同步反映**在 `project-docs/plans/` 下对应的文档中，导致项目文档区长期留存的是一个未能反映最新进度的“僵尸快照”，违背了“同步以供随时查看最新工程进度”的核心初衷。

### 2.2 漏洞 B：`mtime` 导致的“分身”垃圾文件

* **问题所在**：方案明确指定使用 `fs.statSync(planPath).mtimeMs`（修改时间）作为日期前缀 `YYYY-MM-DD` 的来源。
* **最终后果**：对于跨日执行的任务计划，一旦计划内容有更新（例如前一天打钩），其 `mtime` 会变为新的一天。如果在第二天恢复工作（resuming）并再次触发同步分支，会用新的日期前缀生成一个新的副本（例如生成了 `2026-03-03-xxx.md` 的新文件）。而旧的物理副本（`2026-03-02-xxx.md`）仍然残留，从而使得同一个逻辑计划产生多个不同日期的碎片。

### 2.3 漏洞 C：防卫性编程不足

* **问题所在**：在 `syncPlanToProjectDocs` 中，虽然使用了 `mkdirSync({ recursive: true })` 和 `try-catch` 包裹，但在获取 `statSync(planPath)` 时没有做存在性校验（`existsSync`）。此外，对目标目录的文件读写权限也较少进行前置校验。
* **最终后果**：在异常情况下，可能会产生意想不到的错误回溯或是静默失败。

### 2.4 漏洞 D：命名规范与扩展名双重拼接

* **问题所在**：`getPlanName(planPath)` 如果它返回的名字内部已经带有 `.md` 后缀，再经过 `${dateStr}-${planName}.md` 拼接，可能生成形如 `xxx.md.md` 的文件名，造成命名不规范。

### 2.5 策略违规：违反 TDD 与测试强制标准

* 原 `.sisyphus/plans/plan-to-project-docs-sync.md` 中的 QA 策略标明 `Automated tests: Tests-after (先实现，后补充测试)`。这直接违背了我们内部强制的 TDD 测试驱动开发规范。核心的文件 IO 系统集成，绝不应将单元测试视为“可选”（Optional）。

---

## 3. 深度优化方案设计

为了彻底解决“进度状态不同步”与“历史文件残留”的两大痛点，并且符合整洁架构的要求，建议采用以下重构与优化方案。

### 3.1 核心方案建议：采用软链接（Symlink）机制【强烈推荐】

**设计思路：**
摒弃落户物理 `copy` （读写操作），改为文件系统级别的魔法映射 —— **软链接 (Symlink)**。让 `project-docs/plans/YYYY-MM-DD-{name}.md` 成为指向 `.sisyphus/plans/{name}.md` 的符号链接。

**收益与表现：**

1. **绝对的单源真相（Single Source of Truth）：** 一处修改（对原始 plan 打钩 `[x]`），处处即时反映。`project-docs/` 中的表现不仅是最新进度，更是实时的。没有延迟，没有状态分歧。
2. **优雅解决“分身”副作用：** 我们不依赖动态的 `mtime` 生成前缀，而是结合方案 3.2 固定基准时间。
3. **零 IO 开销：** 无需反复读取和写入文件体。

### 3.2 生命周期时间锚定与统一归档

在时间戳选择与命名约束上进行规范化：

* **固定日期前缀**：使用 `boulder.json` 的 `started_at` 字段作为提取日期的唯一来源，或者是提取该计划文件**本身的创建时间 (`birthtime`) 而非修改时间 (`mtime`)**。这样，即使经过多次跨天修改，其在 `project-docs` 中的归档名称也是恒定不变的，从而实现链接（或文件）被正确的覆盖。
* **解耦命名规则**：编写一个通用的格式化工具函数：`ensureDocumentNamingConventions(baseName, dateReference)`，在里面使用 Regex 清理不符合预期的 `.md` 多重后缀。

### 3.3 测试策略的归正 (TDD)

新方案重构必须遵循严格的测试纪律：

1. **Test First:** 在修改 `start-work-hook.ts` 前，先编写 Vitest 单元测试覆盖。
2. **隔离外部依赖 (Mock FS):** 运用 `vi.mock("node:fs")` 模拟对文件系统软链接创建、存在检查等 `fs` API，验证不同场景下的逻辑（目录不存在、覆盖已存在的死链接、非法命名等情况）。
3. **集成测试：** 由于我们处理的是真实的文件 IO 模型，可考虑提供一套局部的集成测试确保 `Symlink` 及目录拼接的真实表现行为符合预期。

## 4. 后续执行建议

在当前粗暴版本（Copy方案）跑通并验证其作为 Hook 被顺利唤起后，应该开启下一个周期的重构任务。届时我们会依照此设计文档作为指导思想，使用 TDD 的方式，将代码重构为基于 Symlink 的健壮版本。
