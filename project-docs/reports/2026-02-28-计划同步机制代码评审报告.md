## 2. 发现的缺陷与改进建议

### 🚨 致命缺陷 (Critical)：绝对路径的跨环境破坏问题

* **问题所在**：在 `sync-plan.ts` 中的软链接创建：

  ```typescript
  symlinkSync(planPath, targetPath)
  ```

  该逻辑直接使用了物理绝对路径，导致推送到远程仓库后，在其他协同开发者的电脑或主干 CI 系统中出现**死链（Broken Symlink）**，严重破坏了 Git 的多人协作特性。
* **修复方案**：应使用相对路径（相对于目标文件所在的目录）生成 Symlink 实体。

  ```typescript
  import { join, relative, dirname } from "node:path"
  // ... 其他逻辑
  const relativePlanPath = relative(dirname(targetPath), planPath)
  symlinkSync(relativePlanPath, targetPath)
  ```

* **关联修改**：测试文件 `sync-plan.test.ts` 中针对软链接解析（`readlinkSync`）的断言也必须同步更改为 `toBe(relative(...))` 的形式。

### ⚠️ 关键缺陷 (Important)：防卫性删除死链失败的 EEXIST 运行时异常

* **问题所在**：清理旧软链的防卫性编程由于 `fs.existsSync` 的行为差异失效：

  ```typescript
  if (existsSync(targetPath)) {
    rmSync(targetPath, { force: true })
  }
  symlinkSync(...)
  ```

  在 Node.js 中，如果 `targetPath` 自身是一个软链接，但其指向的目标文件已经丢失（死链接），`existsSync(targetPath)` 会返回 `false`。这意味着此时 `rmSync` 会被跳过，并在紧接着执行 `symlinkSync` 时引发挂掉的运行时错误：`Error: EEXIST: file already exists`。
* **修复方案**：完全依赖 `rmSync` 配合 `force: true` 的幂等安全性特点来强制扫除环境（移除多余的判断）：

  ```typescript
  // 无论目标是不是文件、软链抑或是死链，直接将其无条件抹除即可
  rmSync(targetPath, { force: true })
  symlinkSync(relativePlanPath, targetPath)
  ```

### 💡 次要建议 (Minor)：清理未使用的引入

* **问题所在**：在 `sync-plan.ts` 文件顶部引入了未被使用的 API：

  ```typescript
  import { existsSync, mkdirSync, statSync, lstatSync, symlinkSync, rmSync } from "node:fs"
  ```

* **修复方案**：应当清理掉 `lstatSync` 以保持源代码树的整洁度。
